# ADR-004: 線路・番線・駅のデータモデル（グラフモデル）

**日付**: 2026-02-22
**ステータス**: Accepted

---

## コンテキスト

鉄道ダイヤエディタでは、以下の現実的な線路構造を表現する必要がある。

- 複々線（急行線・緩行線など、駅間に複数の線路）
- 駅構内の番線（列車によって停まるホームが異なる）
- 分岐・連絡線（別路線への乗り入れ経路）
- 信号場（番線を持たない通過ポイント）
- 駅間に複数路線を経由するケース（例: 相鉄・JR直通線の武蔵小杉〜羽沢横浜国大間）

将来拡張として、不正な追い越し・すれ違いの検出、駅番線の自動割り振り、Track間の進入可否ルール定義を見据える。

---

## 決定事項

### 1. グラフモデル（Node=Track、Edge=TrackConnection）を採用

駅構内番線・駅間本線・連絡線をすべて `Track`（Node）として統一表現し、Track間の接続関係を `TrackConnection`（Edge）で管理する。

MVPでは複線を前提とし、TrackとTrackConnectionをユーザー入力から自動生成する。番線の明示的な編集UIは将来拡張に委ねる。

### 2. Track のフィールド設計

- `Track.kind` は持たない（TrackConnectionを辿ればトポロジーは導出可能で冗長）
- 番線Trackのみ `stationId: Id | null` で駅と関連。駅間本線・連絡線は `null`
- 冗長フィールドを排除し、整合性維持の対象を最小化する

### 3. RailwayLine の責務

- 物理インフラの管理単位。Trackを路線単位でグループ管理する入れ物
- 連続区間の重複は許容しない。境界Track/Stationの共有（直通運転接続部）のみ許容
- 湘南新宿ラインのような運転系統は将来の系統モデルで表現する
- `stationIds` は持たない（trackIds → Track.stationId から導出可能）
- `Track.lineIds: Id[]` とした理由: 境界Trackは複数路線に帰属する実態があるため

### 4. 列車の走行経路表現

`TrackTime` のみで経路と時刻を一元管理する。駅時刻は `trackId → Track.stationId` を辿って取得する。

### 5. TrackTime の時刻 null ルール

バリデーションで担保する（詳細はデータモデルSkill参照）。

---

## 却下した選択肢とその理由

| 選択肢 | 却下理由 |
|--------|---------|
| 駅間TrackリストによるRailwayLine拡張 | 駅構内追加時に根本的な設計見直しが必要になる手戻りリスクが高い |
| 純粋グラフ（MVPでも明示的グラフ管理） | MVPのユーザー入力コストが高すぎる |
| RailwayLine廃止してDiagramViewSectionに統合 | インフラ管理と表示設定の責務が混在する。ビューの柔軟な変更時にインフラ定義が汚染される |
| StationTimeとTrackTimeの独立 | 時刻情報の二重管理が生じる |
| StationTimeにplatformTrackIdを持たせる案 | 同上 |

---

## MVPでの実装方針

ユーザーに「複線/単線」の設定のみを入力させ、TrackとTrackConnectionを自動生成する。

### 先送りにする機能

- 番線の明示的な入力・編集UI
- 複々線・連絡線・信号場の入力UI
- Track間の進入可否ルール
- 競合検出（追い越し・すれ違い違反）
- `trackId → Station` 逆引きキャッシュ

---

## 結果

**ポジティブ**: 複々線・連絡線等を追加概念なしに表現、冗長フィールド排除、将来の競合検出への拡張が素直、インフラ管理と表示設定の責務分離

**ネガティブ**: 自動生成ロジックがMVPに乗る、逆引きのクエリコスト（将来キャッシュ対応）、グラフ整合性維持が必要
